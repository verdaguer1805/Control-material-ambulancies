Defectes comprovats al codi anterior
- Es mostraven estoc/mínim actuals però quantitats antigues de l'esborrany.
  Reobrir només afegia noves necessitats: no recalculava ni retirava les resoltes.
- Els materials de supervisió amb mínim positiu podien continuar mostrant
  consum pendent malgrat haver corregit l'inventari fins al mínim.
- loadRemoteStock omplia files absents amb 300 a la lectura del client.
  Això NO acredita que la base de dades hagi afegit 300 a cap material.
- La lectura global d'inventari no tenia un termini màxim propi.

Canvis
- Un únic càlcul compartit per pantalla, exports i comprovació abans d'enviar.
  Amb mínim positiu: màxim(0, mínim-estoc). Sense mínim, es conserva la cua
  explícita de consum dels materials de supervisió dels submagatzems.
- Esborrany vinculat a la base d'estoc/mínim/necessitat. Si canvia la base,
  recalcular la quantitat automàtica; si es cobreix el mínim, retirar-la.
  Conservar extres explícits i edicions quan la base no ha canviat.
- Confirmació directa per material; confirmat = Registrado + Entregado.
  Sense Propuesto, checkbox o confirmació global addicional.
- Comprovar inventari fresc abans de registrar. Si ha canviat la línia,
  actualitzar-la i demanar revisar-la sense enviar encara.
- Persistir petició immutable abans de l'RPC. Reintentar el mateix ID/payload.
  Conservar també els lots d'enviament antics v285 sense dividir-los.
- Bloqueig de dos enviaments simultanis entre pestanyes amb Web Locks;
  idempotència de servidor mantinguda. En navegadors antics sense Web Locks,
  el mateix ID continua impedint dos payloads diferents o un doble descompte.
- Borrador v2: una pestanya v285 no el pot reobrir com a material sense enviar.
- Lectura: files absents = 0; termini i abort per evitar esperes indefinides.
  No acceptar una resposta tardana o d'una zona substituïda.
