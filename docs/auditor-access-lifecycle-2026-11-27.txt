User-facing behavior
- Cambiar perfil first opens a centered confirmation. Cancel, Escape, or closing
  the app while this prompt is open does not revoke access or clear saved work.
- Only confirming the change calls the server exit operation. A confirmed exit
  deactivates this device; returning afterwards requires authorization again.
- Server-only or local pending work blocks changing profile, including inactive
  profiles. Failed/ambiguous responses do not remove the saved local identity.
- Cancelling a zone edit rechecks the existing active assignment. It never
  grants access and never reactivates an inactive profile silently.
- The mobile and Admin show the same short profile reference for identification.
- Admin shows only Última autorización (Europe/Madrid date and time). Neither
  first registration nor last general update is substituted for that timestamp.

Dates and history
- Authorization date comes from authorize/reassign/reauthorize_preserving_work/
  enable events recorded by the server. Reading/opening the app does not change it.
- Revocation and self-exit retain before/after state and acting authenticated ID.
  Actions distinguish an administrative revoke from leave on the device itself.
- Repeating a successful same-active-assignment request is a retry, not a new
  grant: it preserves revision, dates and pending work. Regranting an inactive
  profile records a new authorization event without changing its first created_at.
- Legacy unknown dates remain unknown; missing past events are not invented.
- Shared authorization codes identify a role, not necessarily the human who
  typed them. Do not present actor_user_id as proof of a named administrator.

Safety boundaries
- Installation does not update any existing grant, assignment, stock or audit.
- New checked Admin revoke is tied to the displayed revision + updated_at and
  cannot revoke a newer reassigned/reactivated grant using an old confirmation.
- Existing owner/supervisor role and zone checks remain unchanged. This is not
  a redesign of organization/lot-scoped administrator credentials.
- Device references represent persisted authentication identities, not hardware
  identifiers. Clearing browser storage/reinstalling can produce another identity.
- Names are not unique identities. No automatic merging/revocation of identical
  names is performed. One-person/one-phone replacement needs explicit verified
  identification; the canceled single-active-by-name migration must not be run.
- Work from other mobile profiles, inventory and completed reports are untouched.
